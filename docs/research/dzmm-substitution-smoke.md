# DZMM 单次回复替换测试

测试日期：2026-09-13。

## 结论

DZMM v1 可以接替部分纯文本回复生成，无需由 DZMM 接管整段会话。使用标准 OpenAI Python SDK，把原有 system 指令及 user/assistant 历史交给它即可。本次还完成了 DeepSeek → DZMM → Qwen 的实际输出接力，身份与上下文保持连续。

这证明了协议兼容和少量场景的承接能力，不保证用户完全察觉不到变化。主要可见差异是响应延迟、措辞和细节保留程度。适合先作为日常聊天、情绪回应和简单解释的候选回复模型；复杂推理、长上下文、多模态和稳定工具调用尚无足够证据。

v2 是另一套需要角色卡的输入协议，可以用于特定角色卡场景，但不是使用 DZMM 生成普通回复的必经路径。

## 测试方式

共 20 次有界短请求，包含 12 次相同用例的模型比较、1 次 v1 流式测试、1 次强制工具调用、4 次 v2 输入兼容性探测、2 次供应商接力。16 次取得正文；其余 4 次返回明确错误，分别是三个不符合 v2 输入要求的请求和一次工具调用请求。

所有内容为合成对话，不含真实聊天、私人人设或群消息。测试读取当前模型配置中的凭据，在独立脚本中直接调用 API，没有启动 MaiBot、修改运行配置或向 QQ 发送消息。

- DZMM：新 v1 地址 `https://api.sillytraven.dev/api/ai/v1`，Neo-16K 和 Dash-0826-16K。
- 对照：当前配置中的 DeepSeek V4 Flash 与 Qwen3.7 Flash，保留各自关闭 thinking 的请求参数。
- 常规用例统一 temperature=0.7、max_tokens=160、非流式；每个模型每题只测一次。每一题的四个模型并发调用。
- 系统要求采用合成的朋友身份、简短中文，以及当前 MaiBot replyer 的纯正文输出约束。
- 原始结果、请求用例、usage 和耗时保存在 [dzmm-smoke-2026-09-13.json](dzmm-smoke-2026-09-13.json)。临时执行脚本位于本机 `temp/dzmm_api_smoke.py`。

## 常规回复与延迟

| 模型 | 更正时间地点 | 情绪回应 | 简单 Python 问答 | 三题中位耗时 |
| --- | --- | --- | --- | ---: |
| DZMM Neo-16K | 正确承接新安排 | 正常短回复 | 解释基本正确 | 7.295 秒 |
| DZMM Dash-0826-16K | 正确承接新安排 | 正常短回复 | 解释正确 | 5.032 秒 |
| DeepSeek V4 Flash | 正确承接新安排 | 正常短回复 | 解释正确 | 3.194 秒 |
| Qwen3.7 Flash | 正确承接新安排 | 正常短回复 | 解释正确 | 2.127 秒 |

耗时是本次客户端请求的墙钟时间，包含网络与服务等待，且输出长度不同；这是少量样本，不是稳定性能排名。

上下文用例先约定下午三点在书店见，随后改成四点半在公园东门。四个模型都采用更正后的时间地点。Neo 初次回复提到热茶，但省略了“两杯”；Dash 额外重述了对方要带的摄影集。没有出现重新自我介绍或重启故事的行为。

情绪用例要求“先别给建议”。DeepSeek 和 Dash 主要表达陪伴；Neo 使用“别憋在心里”，Qwen 建议休息。这说明可正常接话，但语气和约束遵循程度仍有差异，不能用这三个题目宣布风格完全等价。

## 实际供应商接力

同一合成会话保留 system 指令，历史 assistant 文本取自上一供应商的真实返回。

1. DeepSeek 回复了见面安排及自己要带的两杯热茶。
2. 用户追问“那我负责带什么？还有，你叫什么来着？”，切换 DZMM Neo 后返回：**你带摄影集，我叫阿岚。** 本次耗时 11.634 秒。
3. 再切回 Qwen，用户要求不要重复安排，返回：**放心，我肯定准时到。明天见。** 耗时 1.986 秒。

这条链路没有使用 v2 角色卡、服务端 conversation_id 或任何真实会话标识。历史和身份由调用方提供，足以完成跨供应商承接。它不是已经启用到真实 MaiBot/QQ 会话的在线灰度测试。

## v1 与 v2 的边界

| 探测 | 结果 | 含义 |
| --- | --- | --- |
| v1 普通 messages + system | OpenAI SDK 成功解析正文、model、usage、finish_reason | 可用于常规纯文本 replyer |
| v1 stream=true | SDK 取得正确增量正文；首个正文约 6.166 秒，总耗时 6.263 秒 | 流式正文可用；该次没有观察到非空 finish_reason，结束元数据不能假定完全一致 |
| v1 强制调用天气工具 | HTTP 400，content_policy_violation | 该请求未成功；无法据此认定全面不支持 tools，也不能据此替换 planner 的工具调用能力 |
| v2 原样传普通 messages | HTTP 400，user_name is required | 不能原样换 URL |
| v2 带角色卡但保留 system 消息 | HTTP 400，只接受 user/assistant 与字符串 content | 系统要求需映射到 card.system_prompt 等字段 |
| v2 提供 user_name、移除 system，但不提供 card | HTTP 400，card is required | 角色卡是该接口的必要输入 |
| v2 按示例提供角色卡与 user/assistant 历史 | HTTP 200，SSE 正确回复约定，finish_reason=stop | 适配输入后可正常生成 |

成功的 v2 请求使用新建测试 conversation_id，并直接带入已有历史，说明该次调用也能从调用方提供的上下文继续。它不要求对话从第一轮起全部由 DZMM 生成。服务端是否额外存储会话、其它字段是否必填，本次未验证。

该 v2 请求返回 prompt_tokens=1962，而 v1 Neo 的对应历史用例为 159；两次请求的角色卡和包装不同，不能作为等价输入的计费比较。价格与 usage 的结算规则仍未验证。

## 对当前 MaiBot 的建议

保留 DeepSeek/Qwen 承担 planner，先将 DZMM v1 用在纯文本 replyer 的指定场景，复用现有模型池与供应商路由提示词。会话历史、人设和记忆仍由 MaiBot 管理。

若要使用 v2，则增加明确的角色卡映射，处理用户名、允许的消息角色和 SSE 错误格式。当前场景已有可用 v1，不需要为了替换单条回复重构完整对话管理。

上线前仍应做少量受控的实际会话验证，重点观察较长历史下的人设稳定、超时率及语言风格。此次不宣称“完全无感”，也没有自动修改两套实例的供应商地址或启用规则。
